# Dify 接入要点记录

本次查阅的仓库为 `langgenius/dify`。结合仓库首页公开说明，当前可以确认 Dify 适合作为本项目的 **RAG 编排与应用层接口**，原因在于它同时提供工作流、RAG Pipeline、Agent 能力以及可直接集成到业务系统中的 API 能力。

| 观察项 | 结论 | 对本项目的意义 |
| --- | --- | --- |
| Workflow | Dify 支持以可视化方式构建 AI 工作流 | 可将“多模态输入预处理 → 风险识别 → 案例召回 → 报告生成”整理为统一工作流 |
| RAG Pipeline | Dify 原生支持文档导入、解析与检索流程 | 可将反诈案例库、法规库、诈骗话术库纳入知识检索链路 |
| API 能力 | Dify 提供对应 API 以便接入自有业务系统 | 移动端不直接暴露模型密钥，而是经由本项目服务端中转调用 |
| 模型支持 | Dify 支持多种模型供应商与 OpenAI API 兼容模型 | 后续可结合用户要求对接 Qwen 与 Embedding 模型能力 |
| 适用方式 | 既可使用云端也可自部署 | 当前优先按“外部 Dify 服务已存在”的方式预留接入层，避免移动端承担复杂部署 |

基于当前信息，后续实现建议如下：移动端负责多模态输入、记忆展示、预警与报告 UI；本项目服务端负责和 Dify 对接；Dify 负责 RAG 检索编排与回答生成。按照用户要求，检索层将采用 **Embedding 向量检索** 路线，而不是简单关键词搜索。

## 来源摘要

Dify 仓库首页明确将其描述为一个用于 agentic workflow 开发的生产级平台，并列出 **Workflow、RAG Pipeline、Agent capabilities、Backend-as-a-Service API** 等核心能力。这说明其定位并非单一聊天前端，而是可承接本项目反诈 RAG 编排需求的中间平台。

## 官方 API 集成结论补充

根据 Dify 官方 API 文档，Dify 的应用能力应通过自有业务后端进行调用，而不应在前端直接暴露 API Key。文档明确建议将密钥保存在后端环境变量中，并在转发请求前执行请求校验、速率限制和日志记录。这与本项目的移动端架构要求一致，因此后续将采用“**移动端 → 本项目服务端 → Dify API**”的接入方式。

| 接口主题 | 关键结论 | 对本项目的落地方式 |
| --- | --- | --- |
| 鉴权方式 | 使用 `Authorization: Bearer {API_KEY}` 调用 Dify API | 仅在服务端保存与使用密钥 |
| 文本生成 | 可调用 `completion-messages` 获取文本生成结果 | 可用于安全报告总结、建议生成等单轮输出 |
| 对话应用 | 可调用 `chat-messages` 建立连续对话 | 可用于反诈追问、风险澄清与多轮分析 |
| 会话保持 | Dify 返回 `conversation_id`，后续调用需继续携带 | 可与本项目短期记忆做映射，保证会话连续性 |
| 变量管理 | 同一会话中可结合会话变量调整行为 | 可与长期记忆标签、用户角色画像联合使用 |
| 安全要求 | 不要在前端代码或客户端请求中暴露 API Key | 移动端只请求本项目服务端，不直接访问 Dify |

对于本项目而言，`conversation_id` 可以作为 **Dify 会话态** 的外部标识，而应用内部仍需保留自己的短期记忆缓存。这样做的好处是，Dify 负责工作流与应用级对话上下文，本项目则负责补充用户特定的风险画像、近期事件和本地状态，从而实现“Dify 会话记忆 + 本地长短期记忆”的协同模型。
